## Chat channels: Telegram, iMessage and WhatsApp (Hono webhooks + account linking + Claude chat agent)

- Architecture (2026-11-20): one shared pipeline, one adapter per channel. `src/channels/types.ts` defines `InboundMessage` (normalised message, the Inngest event payload) and the `Channel` adapter interface (sendText with optional link/reply threading, sendTyping, downloadAttachment, sendFile, limits, reply style for the prompt). Adapters: `src/telegram/channel.ts` (`telegram`), `src/linq/channel.ts` (`imessage`) and `src/whatsapp/channel.ts` (`whatsapp`), registered in `src/channels/index.ts`. Adding a channel (e.g. SMS or Messenger): add it to `PLATFORMS` in `src/db/schema.ts` + `npm run db:push`, write an adapter, register it, add a webhook route in `src/app.ts` that verifies and parses into an `InboundMessage` and calls `routeMessage`. Nothing else changes.
- Flow: platform -> Hono webhook (`src/app.ts`) verifies the request (401 otherwise) and parses it (`parseTelegramUpdate` / `parseLinqWebhook` / `parseWhatsAppWebhook`; null or empty = ignore) -> `handleInbound` (`src/channels/router.ts`) looks `(platform, senderId)` up in `channel_identifiers`:
  - not linked, with `verifiedPhone` (the iMessage sender's own number; WhatsApp's `from`, or the number shared with WhatsApp's contact-request button; on Telegram a contact shared with the "Share my phone number" button whose `user_id` equals the sender's id) -> in-chat sign-up, no browser: `findOrCreatePhoneUser` (`src/auth/clerk-phone.ts`) finds the Clerk user with `external_id` `phone:+<E.164>` or creates one through the Backend API (username `u<digits>`, `private_metadata.phone`, no email, no password), `linkAccount`, "Welcome / You're connected (0712 ••• 678)", then routing continues as linked (so the same message gets the payment prompt or goes to the agent). The same number on Telegram, iMessage and WhatsApp is one account (verified 2026-11-21 for Telegram -> iMessage in a test, and for WhatsApp sign-up live). Clerk's phone sign-in (SMS) is a paid feature and isn't used: the number is data, not an identifier. Instance settings changed 2026-11-21 for this: email optional at sign-up, usernames on (optional). Accounts created this way can't sign in on the web until they add an email; payments use a placeholder email `<user id>@<railway domain>`.
  - not linked, no number, on a channel with `canRequestPhone` (Telegram; WhatsApp users who hide their number behind a username) -> a share-number button (`SendOptions.requestPhone`: Telegram reply keyboard, WhatsApp `request_contact_info`), plus "send /connect to sign in with Google or email".
  - not linked otherwise (`/connect` on Telegram or WhatsApp, iMessage from an Apple ID email) -> event `chat/link.requested` `{ message, linkKey }` -> `link-account` (`src/inngest/link.ts`), the browser device flow. Linking always comes first.
  - Not handled yet: a user who linked through the browser (Google/email, device flow) and later arrives from another app by phone gets a second, phone-based account; there is no account merge (suggested fix, not built: let browser-linked users share their number to tag their account with `phone:+...`).   - linked, no Pro (`hasPro`, `src/billing/pro.ts`) -> `handleUnpaid`, never the AI: a Kenyan number in the message -> event `billing/payment.requested` -> `mpesa-payment` (M-Pesa STK push, see "Payments"); a payment waiting for the PIN (< 4 min old) -> "still waiting" for the same number or no number, but a *different* number replaces it (old row marked failed "replaced by a new number", new STK push; `mpesa-payment` singleton mode `cancel` stops the waiting run; if the old prompt is still paid, the webhook credits it anyway); anything else -> price + "reply with your M-Pesa number". ## Payments: M-Pesa STK push via Paystack (2026-11-21)

- Pro is a pass, not a subscription: Paystack can't charge M-Pesa again automatically (recurring charges are cards only), so each payment adds `PRO_PERIOD_DAYS` to `pro_access.pro_until` and the user pays again when it ends. Price `PRO_PRICE_KES` in `src/billing/pro.ts`: KES 2 / 30 days for testing the LIVE keys (the user's choice); raise it for real use. Free users are blocked; no reminders; M-Pesa only (Paystack also has Airtel, provider `atl`).
- Flow, all inside the chat: non-Pro message -> price prompt; user sends a number (`findKenyanPhone`: 07/01/7../254/+254, normalised to +254...) -> `billing/payment.requested` (id = reference `pa-<platform>-<message id>`, so resends dedupe) -> `mpesa-payment` (`src/inngest/payment.ts`, singleton per Clerk user, mode cancel): email from Clerk, `createPayment` row, `POST /charge` (`currency KES`, `mobile_money { phone, provider: 'mpesa' }`, amount in subunits), "check your phone" reply, `waitForEvent billing/payment.settled` 200 s (the STK prompt expires after 180 s), then `settlePayment` (+ two re-checks after 30 s / 90 s), then "Payment received (M-Pesa receipt X), Pro until <date>" or "didn't go through (<reason>), send your number again".
- `POST /webhooks/paystack` (URL set in the Paystack dashboard): raw-body signature check (`x-paystack-signature` = HMAC-SHA512 keyed on the secret key; or `Paystack-Signature` with `PAYSTACK_WEBHOOK_SECRET` if set), then for `charge.*` events `settlePayment(reference)` and `billing/payment.settled`. Unknown references answer 200 `handled: false`. Errors answer 503 (Paystack retries for 72 h).
- `settlePayment` (`src/billing/pro.ts`) is the only way Pro is granted: it asks `GET /transaction/verify/:reference`, requires status `success` with the same amount and currency, and in one transaction moves the row pending/failed -> success and extends `pro_until` (`greatest(pro_until, now()) + period`). Calling it again does nothing, so webhook resends and the function's own checks never count a payment twice; a success after we marked it failed (timeout) is still credited.
- Agent tools for Pro users (`src/agent/billing-tools.ts`): `check_pro_status`, `start_mpesa_payment` (renew early; sends the same event). The model can't grant Pro.
- Tables: `payments` (reference PK, clerk_user_id, phone, amount in subunits, currency, status pending/success/failed, period_days, failure_reason, receipt, paystack_id, created_at, settled_at) and `pro_access` (clerk_user_id PK, pro_until). Phone numbers are stored only in `payments`, masked in replies (`maskPhone`, `0712 ••• 678`; not `***`, which WhatsApp/Telegram treat as formatting), never logged.
- Env: `PAYSTACK_SECRET_KEY` (the local `.env` has it as `PAYASTACK_SECRET_KEY`, sic; both are accepted). The `.env` keys are LIVE (`sk_live_`): every real STK push charges real money. Local tests use a stubbed verify API or an invalid key (`PAYSTACK_SECRET_KEY=sk_test_deliberately_invalid npm run dev`), never a real number with the live key. The public key isn't used.

## Sentry (errors, tracing, logs, AI agent monitoring)

- Org `hardhaven`, project `personal-assistant-server` (platform `node-hono`, EU ingest). CLI: `sentry` (in `~/.local/bin`, logged in), e.g. `sentry issue list hardhaven/personal-assistant-server --period 24h`, `sentry log list ...`, `sentry trace view hardhaven/personal-assistant-server/<trace id>`, `sentry event analytics ... --dataset spans` (shows dropped spans and why).
- `src/instrument.ts` calls `Sentry.init` from `@sentry/hono/node` and is loaded with `--import` before the app (`dev` and `start` scripts), which also registers the hook that instruments `@anthropic-ai/sdk`. Nothing is sent without `SENTRY_DSN`; `SENTRY_DEBUG=1` prints what the SDK sends or drops. Environment is `development` when `INNGEST_DEV` is set, else `production` (override `SENTRY_ENVIRONMENT`); release = `RAILWAY_GIT_COMMIT_SHA`; traces 100% locally, 10% in production.
- Privacy: HTTP bodies, AI prompts/outputs, DB query data and stack-frame variables are not collected (`dataCollection`), because users' chats and files pass through. AI spans carry model, tokens, cost, latency, tool names, user id and conversation id only. Change that only deliberately. The Telegram bot token (in Telegram API URL paths) is replaced with `[Filtered]` in spans, events, logs and breadcrumbs (`scrub` in `instrument.ts`); keep that when adding hooks.
- Logs: `log.info/warn/error(message, attributes)` from `src/log.ts` (Sentry Logs + one stdout/stderr line). Attributes are metadata only (ids, counts, sizes, durations, statuses): never message text, file contents, phone numbers or emails, so never `senderId`. In Inngest functions, log inside `step.run` (the function body re-runs on replay). Main lines: `message routed` (router), `chat turn answered` (one per reply: model/tool calls, tokens, latency, stop reason), `chat turn skipped`/`chat turn failed`, `account link sent/linked/not completed`, `sandbox created/started`, `tool returned an error`/`tool failed`, `webhook rejected`/`webhook routing failed`. `console.warn/error` from libraries still reach Sentry Logs through `consoleLoggingIntegration`.
- AI agent monitoring: `answer()` is an `invoke_agent assistant` span; Sentry's Anthropic integration adds a `chat claude-sonnet-5-5` span per model call (tokens, cost); `durable()` adds `execute_tool <name>` spans. `chat` sets `Sentry.setUser({ id })` and `setConversationId(clerkUserId)`, so a user's turns group into one Sentry Conversation. Spans inside steps are siblings of the agent span in the trace, not its children (steps run in Inngest's execution context).
- Inngest: our own `src/inngest/sentry-middleware.ts` (replaced `@inngest/middleware-sentry` on 2026-11-21: it continued traces without a dynamic sampling context, so Sentry v11 dropped every span of a run as `missing_dsc`, and it attached the event payload, i.e. message text, to spans). One trace per run (trace id derived from the run id, sampled per run), spans per request and executed step, function failures captured on the final attempt.
- `src/app.ts` has `app.use(Sentry.sentry(app))` (request traces, errors reaching `onError`). Webhook routing failures (answered 503) are captured as issues and logged.

### Conversation management (planned, not built)

Today each Clerk user has one endless conversation: one transcript file, and only the last 40 messages (`MAX_CONTEXT_MESSAGES` in `src/agent/transcript.ts`) go to the model. It never overflows, but older facts are forgotten, unrelated topics get mixed in the same window, and every reply pays for up to 40 old messages. Planned fixes, in order:

1. Long-term memory: a short per-user note of lasting facts (name, city, preferences, ongoing projects), sent with every message. Before messages leave the 40-message window, the model saves anything worth keeping into it.
2. `/new` (or "new topic"): starts a fresh conversation, keeping the long-term memory but not the old messages. Works the same on every channel because it's just a message.
3. Named topics/projects (good Pro feature): `/topic CV`, "switch to my trip", "what topics do I have?". Each topic has its own transcript and its own sandbox folder; the model can ask "start a new topic for this?" when the subject changes.
4. Use channel features where they exist: Telegram may support topic threads in private chats with bots in recent Bot API versions (check the current Bot API docs before relying on it; the code already passes `message_thread_id`). WhatsApp and iMessage have no threads, only quoted replies, so use commands there. On every channel, include the quoted message when the user replies to an older one.
5. A search tool over the user's full history, so older conversations stay reachable.

Recommended first step: 1 and 2 (small, same on all channels); 3 later, possibly Pro-only.
